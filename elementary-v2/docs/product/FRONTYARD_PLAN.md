## 2. 화면 (사용자 시안 기준)

학교앞마당 = 학교 선택("○○초등학교 주변") → 행동 카드 두 개("소식 올리기" 학원용, "필요한 활동 남기기" 부모용)
→ 칩(전체 · 모집해요 · 찾아요, 이어서 학원·과외 · 돌봄 · 등하원을 가로 스크롤) → 목록.
칩 이름은 말머리와 같게 쓴다(시안의 '모집 소식 · 부모의 관심'을 바꿈).

시안에 더하는 것:

- [찾아요] 카드에 **"저도 필요해요 N"**. 글을 쓰는 사람보다 누르는 사람이 많고, 이것이 학원에 보일 수요 숫자다
- [모집해요] 카드에 학원명·운영자 확인 여부, 마지막 확인일, 모집 상태, "내 시간표에 담기". 목록 아래 "학교 공식 프로그램이 아니에요"
- [어디초 소식]은 칩을 두지 않는다. '전체'에서 맨 위 고정 1개, 아래에 "어디초 소식 모두 보기"(같은 피드 함수의
  `p_post_type = 'notice'`). 그 학교 글이 3개 미만이면 빈 자리를 소식 카드로 채우고, 지역 글이 늘면 자동으로 줄어든다.
  '모집해요'·'찾아요' 칩을 고르면 소식은 보이지 않는다
- 시간표 빈칸에서 들어오면 학교·학년·요일·시간이 채워지고 "화 14:00~16:00 ×" 조건 칩이 붙는다
- 학교 기본값: 시간표에서 고른 학교(`activeSchoolId`), 없으면 검색
- 우리 학교 글이 없으면 같은 구 글과 "첫 관심을 남겨 보세요"
- 학교별 앞마당 페이지는 글이 쌓일 때까지 `noindex`(빈 페이지 6,302장 색인 방지)

## 3. 데이터 원칙 (인수인계서 8절 + 사용자 검토 이미지)

1. 공식 공급(학원 프로그램) · 개인 일정 · 공개 게시글은 다른 테이블이다
2. 개인 일정은 `visibility = 'private'` 고정. 공개 글로 바뀌는 경로가 없다
3. 부모 입력이 여러 건 일치해도 공식 정보로 자동 승격하지 않는다. 공식 정보는 학원 등록 또는 운영자 확인(`admin_verified`)뿐
4. 예상/실제 이용을 구분한다. 시간표에 넣었다고 이용 확정이 아니다(엔진의 `participation` → `schedule_status` 파생)
5. 요일마다 시간이 다를 수 있어 시간은 회차(sessions) 행으로 둔다
6. 집계는 개인정보처리방침에 목적을 적은 뒤, 최소 인원 이상일 때만
7. 학원 키는 `etl/academy_institutions.py`의 `institution_key`(`neis:{교육청코드}-{지정번호}`, `dojo:…`). 지정번호만으로는 전국 유일하지 않다

## 6. 안전장치 (익명 공개 글)

- 모든 쓰기는 함수 경유. 테이블 권한은 SELECT뿐
- 제목·본문에 전화·이메일·오픈채팅 패턴이면 저장 거절(화면도 같은 규칙으로 먼저 막음)
- 하루 글 3개, 신고 20건 제한. 서로 다른 3명이 신고하면 자동 숨김
- 신고 사유에 '광고성 [찾아요]'(`ad_disguised`) — 말머리를 지키게 하는 장치
- [찾아요]는 학교 단위 범위만, 게시 기간 기본 30일(최대 90일) 뒤 자동 마감
- 아동 실명·집 주소·귀가 동선은 입력 칸 자체를 두지 않는다

## 7. 열린 질문

- 익명 세션을 페이지 진입이 아니라 첫 저장·첫 "저도 필요해요" 때 만든다 — 방문자·크롤러마다 계정이 생기지 않게. 화면 구현 때 확인
- [모집해요] 등록 요청에서 운영자가 학원 본인임을 무엇으로 확인할지(등록번호 대조, 대표번호 회신 전화)
- 학원법상 교습비 표시 등 광고 표시사항
