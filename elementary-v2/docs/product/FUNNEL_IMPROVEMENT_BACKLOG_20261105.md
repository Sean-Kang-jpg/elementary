## 목표와 근거

검색으로 들어온 사람이 관심 학교를 확인하고, 그 학교의 주간 시간표를 만들고, 다시 열어 사용할 수 있게 한다. 입학 일정만 확인하려는 방문자는 별도 성공 경로로 본다.

2026-11-05 로그인된 GA4 `wherecho` 속성 557166556과 운영 사이트 직접 점검을 근거로 한다. 최근 기간은 10/8~11/4, 비교 기간은 9/10~10/7이다.

| 확인된 사실 | 작업에 반영할 판단 |
| --- | --- |
| 세션 226 / 이전 58, 전체 이탈률 39.38% / 이전 70.69% | 유입 전체의 즉시 이탈 문제로 단정하지 않는다 |
| 홈 78세션, 사립초·국립초 가이드 63세션 | 상위 랜딩부터 다음 행동을 개선한다 |
| 학교 상세 조회 40명, `/timetable` 조회 8명 | 서로 연결된 순차 퍼널은 아직 아니며 도달 이후를 측정해야 한다 |
| `/timetable` 자연 검색 사용자 2명, 모바일 사용자 6명·해당 경로 평균 참여 5초 | 검색·모바일 동선을 우선 확인한다. 적은 표본으로 원인을 확정하지 않는다 |
| 시간표 저장 성공 이벤트 확인 불가, 경로만으로 page_view 중복 방지 | UI 개선 효과를 판단할 계측부터 보완한다 |
| 운영은 4문항 시작 흐름, 점검한 로컬 소스와 차이 있음 | 실제 배포 기준을 먼저 확정한다 |

`/timetable` 집계에는 입학까지와 우리 아이 한 주가 섞여 있다. `plan_start`는 최초 일정 시작이며, `save_candidate`는 관심 후보 저장이다. 어느 것도 주간 시간표 저장 완료의 대용 지표로 쓰지 않는다. 기존 UX-01·UX-07·UX-08d 완료 상태는 유지하고, 아래 카드는 후속 개선으로 관리한다.

## 범위와 작업 운영

- GNB ‘우리집 일정’, ‘입학까지 / 우리 아이 한 주’ 두 화면, 기존 URL·저장 키·저장 형식은 유지한다.
- 계정·기기 간 동기화, 새 DB, 학교·돌봄 원천 데이터 변경은 이번 범위 밖이다.
- 예상 크기: S 반나절 이하, M 하루 안팎, L 여러 날. **실제 일정 약속이 아닌 초기 추정**이며 FNL-00 뒤 재산정한다.
- 담당 표기는 권장 역할이다. C=닫힌 범위 구현, K=구조·상태·통합 검토, U=제품·콘텐츠 사실·GA4 관리. 실제 담당자는 착수 시 확정한다.
- 구현은 카드별 작업 브랜치에서 진행한다. 현재 작업 폴더의 다른 미커밋 변경을 묶거나 덮어쓰지 않는다.
- 모든 카드는 초기 상태 `todo`. 결과·검증 기록이 채워지고 완료 기준을 충족해야 `done`으로 바꾼다. 문서에 적힌 기존 완료 표시만으로 새 카드를 완료 처리하지 않는다.

### FNL-01 · P0 · 주간 시간표 이벤트 계약 확정

- 담당/크기: C + K 검토 / S. 의존: FNL-00.
- 작업: `MEASUREMENT_PLAN.md` 10절에 이벤트 의미·발화 주체·재진입·중복 규칙을 정의한다. 기존 의미가 맞는 이벤트는 재사용하고, 다른 의미의 이벤트를 저장 완료로 바꾸지 않는다.
- 제안 계약: `timetable_view(face)` 실제 화면 표시, `timetable_school_pick` 유효 학교 선택/지정 진입 완료, `timetable_draft_create` 초안 최초 저장 성공, `timetable_first_edit` 초안별 세션 내 처음 수락한 실제 사용자 변경(쓰기 시도 전), `timetable_save_success` 사용자 변경 저장 성공, `timetable_save_failure` 저장 실패. 초안 생성과 일반 저장 성공은 같은 쓰기에서 중복 기록하지 않는다. 첫 편집 이벤트 자체는 저장 완료가 아니다.
- 대상: `MEASUREMENT_PLAN.md`, `src/utils/analytics.ts`. 필수 맥락은 통제된 `entry_point`, `face`, 필요 시 공개 `school_id`, 성공/실패 코드, `measurement_version`이다. 이벤트 이름·타입은 이 카드에서 확정한다.
- 완료 기준: 새 방문·직접 학교 링크·기존 초안·학교 전환·뒤로가기·쓰기 실패의 기대 이벤트 표가 있다. `plan_start`·`save_candidate`와 구분된다. 최초 입력만 하고 저장하지 않은 행위를 완료로 세지 않는다.
- 검증: 학교 선택 없이 주간 화면을 연 경우, 자동 복원, 실제 사용자 선택의 차이를 계약으로 재현할 수 있다. 아동 이름·일정명·주소·귀가 시각·사용자 입력값은 전송하지 않는다. 분석용으로 새 기기 저장 키를 만들지 않는다.

### FNL-02 · P0 · 화면·학교 쿼리 전환 계측 누락 수정

- 담당/크기: C + K 라우팅 검토 / M. 의존: FNL-01.
- 작업: `App.tsx`의 pathname만 비교하는 page_view 판정을 의미 있는 화면 주소 기준으로 바꾼다. 해석된 `face`·학교를 반영하고, UI 표시 후 FNL-01의 화면 이벤트를 기록한다. `utm_*` 등 추적 쿼리만 변한 경우에는 화면 조회를 늘리지 않는다.
- 대상: `src/App.tsx`, `src/utils/analytics.ts`, 필요 시 의미 있는 주소 판정 순수 도우미, 기존 브라우저 검증 스크립트. URL 구조 자체는 바꾸지 않는다.
- 완료 기준: `timeline → week → 다른 학교 → 뒤로가기`에서 실제 화면 전환당 기대한 이벤트가 한 번씩 발생한다. 초기 링크 복원·주소 정규화·React 재렌더는 중복을 만들지 않는다. 쿼리 없는 기본 화면도 실제 표시된 face와 일치한다.
- 검증: 직접 링크·인앱 링크·새로고침·뒤로/앞으로·학교 변경·같은 학교 재선택을 디버그 기록으로 확인한다. 순수 주소 판정은 의미 있는 분기만 Node 기본 러너로 검증한다.

### FNL-03 · P0 · 선택·생성·저장 성공/실패 이벤트 연결

- 담당/크기: K(저장 경계) + C(분리 가능한 이벤트 도우미) / M. 의존: FNL-01, FNL-00의 실제 파일 확인.
- 작업: 학교 선택 성공과 초안·사용자 변경의 실제 저장 성공/실패 경계에 이벤트를 연결한다. 버튼 클릭을 성공으로 세지 않는다. 현재 배포에서 사라진 것으로 보이는 학교 선택 계측도 계약에 맞춰 복구한다.
- 대상: 실제 시작 질문 컴포넌트, `SchoolSelection.tsx`, `MySchedule.tsx`, `src/utils/schedule/plans.ts` 또는 실제 저장 호출 경계, `analytics.ts`. 저장 형식 변경은 포함하지 않는다.
- 완료 기준: 최초 초안 생성 1회, 첫 실제 사용자 변경 1회/초안/세션, 저장 성공은 실제 사용자 작업당 1회다. 첫 변경의 저장이 성공하면 첫 편집과 저장 성공을 각각 기록하고, 실패하면 첫 편집 뒤 실패만 기록한다. 자동 마운트·복원·변경 없는 저장 시도는 사용자 편집으로 세지 않는다. 여러 localStorage 호출로 한 작업이 중복 집계되지 않는다. 실패하면 성공 이벤트와 성공 UI가 모두 없어야 한다.
- 검증: 빈 초안·자료를 채운 초안·기존 초안 수정·쓰기 실패·학교 자료 요청 실패·재시도·재방문을 확인한다. 첫 편집과 저장 성공은 서로 다른 분석 단계이므로 발생 횟수를 합쳐 전환자로 세지 않는다.

### FNL-04 · P0 · GA4 보고서와 새 기준선 구성

- 담당/크기: U(GA4 관리) + C(조회·명세) / M. 의존: FNL-02·03.
- 작업: 맞춤 정의·주요 이벤트의 현재 설정을 먼저 확인하고 필요한 항목만 등록한다. 저장 성공을 주간 활용의 주요 이벤트로 검토하되, 관심 후보 저장과 분리한다. 주요 이벤트 지정일 이후에는 참여율·이탈률의 정의상 영향이 있을 수 있으므로 이전 수치와 비교 시 변경일을 표시한다.
- 대상: GA4 속성 557166556, `MEASUREMENT_PLAN.md`의 설정·검증 기록.
- 완료 기준: 주간 시간표 퍼널과 입학 일정 퍼널을 별도로 조회할 수 있다. 랜딩·세션 채널·기기별 각 단계 도달 세션 수/분모/전환율이 함께 표시된다. 미등록·처리 지연·계측 이전 구간은 0 대신 확인 불가로 표기한다.
- 검증: DebugView와 처리 완료된 보고서를 구분해 확인한다. 동일 세션 안의 이벤트 순서를 보장할 분석 방법을 명시한다. GA4 탐색에서 그 조건을 재현할 수 없으면 BigQuery 등 가능한 방법과 추가 연결 필요 여부를 기록하며, 사용자 범위 퍼널을 세션 범위로 부르지 않는다. 새 권한·연결은 별도 범위로 둔다.

### FNL-06 · P1 · 선택한 학교로 넘어오면 바로 만들기 시작

### FNL-07 · P1 · 상위 가이드의 다음 행동을 목적에 맞게 연결

- 담당/크기: C, 날짜·내용 변경 시 U 확인 / M. 의존: FNL-01·04.
- 작업: 1차 대상은 `private-national`, `admission-timeline`, `morning-care`, `school-notice`다. 사립 지원·입학 일정은 timeline, 하교·돌봄 계획은 week로 연결한다. 기존 nextStep·담기·일정 API를 우선 재사용한다. 사립 가이드의 모든 유입을 주간 시간표로 돌리지 않는다.
- 대상: 해당 `src/content/guides/*.md`, `NextStep.tsx`, 필요한 경우 `AddToPlanButton.tsx`, 콘텐츠 빌드 검증. 정적 프리렌더가 읽는 콘텐츠도 함께 확인한다.
- 완료 기준: 안내를 읽은 지점 가까이에 목적과 도착 화면을 알 수 있는 주 행동이 있다. 학교를 모르면 학교 선택으로, 알면 해당 학교로 이어진다. ‘일정에 담기’는 실제 항목 저장이 성공한 경우에만 완료를 표시하며 단순 화면 이동을 담기로 부르지 않는다.
- 검증: 모바일·직접 검색 랜딩·이미 담은 항목·저장 실패를 확인한다. 모집 날짜·기관·제도 사실은 이 작업에서 임의 수정하지 않는다. 행동 클릭과 도착·저장이 구분돼 측정된다.

### FNL-08 · P2 · 홈과 학교 미선택 화면에서 시간표 결과를 빨리 이해시키기

- 담당/크기: C(홈) + K(시간표 구조 검토) / M. 의존: FNL-06·07.
- 작업: GNB는 유지하면서 행동 문구에 ‘주간 시간표’를 명시한다. 홈의 기존 일정 예시를 활용하고, 학교 미선택 week 화면의 긴 설명·단계를 줄여 검색과 간결한 결과 예시를 함께 보여준다.
- 대상: `HomePage.tsx`, `HomeShelves.tsx`, `TimetablePage.tsx`, 관련 스타일, 필요한 정적 홈 생성 부분 `scripts/build-shell-pages.mjs`.
- 완료 기준: 신규/기존 사용자 모두 첫 화면에서 기능과 다음 행동을 이해할 수 있고 주 행동이 경쟁하지 않는다. 예시는 실제 사용자 저장값과 분리돼 표시된다. 기존 초안 사용자는 미선택 안내로 되돌아가지 않는다.
- 검증: 360px·390px·데스크톱에서 잘림·가로 넘침·하단 메뉴 겹침·검색 결과·키보드 초점을 확인한다. 이해도 개선은 관찰/배포 후 지표로 평가하며 화면 배치만으로 효과를 확정하지 않는다.

### FNL-09 · P2 · 랜딩 `(not set)`와 초기 조회 품질 진단

- 담당/크기: C / M. 의존: FNL-02. FNL-07·08과 별도로 진단 가능.
- 작업: 최근 13세션의 랜딩 미확인에 대해 초기 page_view·session_start·링크 복원·호스트·측정 제외 조건을 확인한다. 중복 태그·자동 히스토리 조회 설정도 확인한다. 원인을 확인하기 전 전역 필터를 적용하지 않는다.
- 대상: `App.tsx`, `analytics.ts`, GA4 스트림 설정, 기존 초기 로딩/브라우저 검증.
- 완료 기준: 재현 경로와 원인 또는 아직 판별 불가한 가설을 구분해 기록한다. 재현된 코드 결함만 수정하고, GA4 설정 변경은 영향·적용일을 남긴다. 미확인 방문을 임의 삭제해 비율을 낮추지 않는다.
- 검증: 홈·학교·가이드 직접 진입, 복원 실패, 느린 네트워크, 자동화 제외·디버그 기록을 확인한다. 일반 보고서 지연과 실제 초기 조회 누락을 구분한다.

### FNL-10 · P1 · 전체 동선 검증·배포 기록·효과 재점검

- 담당/크기: C(검증) + K(통합) + U(배포 결정) / M + 관찰 기간. 의존: 각 배포 묶음의 구현 완료.
- 작업: 새 방문/기존 초안으로 홈·주요 가이드·학교 딥링크에서 실제 첫 편집과 저장·재열기까지 확인한다. 소스·화면·이벤트를 같은 기준 버전으로 기록한다.
- 완료 기준: 아래 공통 검증을 통과하고 저장 실패도 확인한다. 운영 배포 시각·커밋·measurement_version·GA4 설정 변경일이 남는다. 수정 전후 비교는 새 계측 기준이 동일한 구간만 사용한다.
- 결과 판정: 배포 7일 뒤 계측 정상 여부·정성적 막힘을 우선 확인하고, 처리 완료된 28일 구간으로 도달 세션 수와 비율을 재검토한다. 적은 분모는 그대로 공개하며 유의미한 개선을 단정하지 않는다. 채널 구성 변화도 함께 본다.
- UX 가설의 판단 지표: 학교 상세 → week 도달률, week → 첫 편집률, 첫 편집 → 저장 성공률, 저장 → 재열기. 가이드 → timeline 담기 성공은 별도다. 개선 목표치는 기준선 확보 후 정하며 이번 감사 수치에서 임의로 만들지 않는다.

## 공통 완료·검증 기준

- 실행 위치: `pjt_250826/elementary-v2/`.
- 프론트엔드 변경: `npm run lint`, `npm run typecheck`, `npm run build`, `npm run browser:smoke:public -- http://127.0.0.1:3000`. 로컬 실행 포트가 달라지면 실제 URL을 명시한다.

- 브라우저 검증은 기존 자동화 제외·분석 디버그 모드를 사용해 GA4 운영 수치를 오염시키지 않는다. DebugView 확인은 분리된 점검 방문으로 기록한다.
