# ADR-006: 상세 페이지는 크롤러 대상 서버리스 프리렌더로 제공한다

Status: Proposed
Date: 2026-09-26
Context: [`../product/PRODUCT_CONCEPT.md`](../product/PRODUCT_CONCEPT.md) 12절 0단계 항목 3

## 문제

컨셉 v1.1의 유입 전략은 학교·아파트 상세 페이지가 검색엔진에 색인되는 것을
전제한다. 현재 앱은 순수 CSR SPA다.

- [`index.html`](../../index.html)은 정적 `<title>` 하나를 갖는다
- [`vercel.json`](../../../vercel.json)은 모든 경로를 `index.html`로 rewrite한다
- 라우팅 자체가 없다 (`react-router` 미설치, `history.pushState` 사용 0건)

`react-helmet` 류로 제목·설명을 동적 주입해도 충분하지 않다. 구글은 JS를
렌더링하지만 지연되고 불완전하다. 네이버 Yeti는 JS 렌더링이 **불가능하지는
않으나 신뢰할 수 없는 것으로 알려져 있고**, 네이버 대상 기술 SEO 가이드는
일관되게 서버 렌더 HTML을 권한다. 한국 학부모 대상 서비스에서 네이버 색인을
운에 맡길 수는 없다.

## 규모

| | 학교 | 아파트 단지 | 지역 | 합계 |
| --- | --- | --- | --- | --- |
| 수도권 빌드 (측정치) | 2,260 | 20,164 | ~200 | **22,624** |
| 현재 운영 공개 (6개 광역) | 2,659 | ~23,700 (추정) | ~300 | **약 26,700** |
| 전국 확장 완료 시 (17개 광역) | 6,303 | ~56,000 (추정) | ~800 | **약 63,000** |

측정된 값은 수도권 빌드 한 줄뿐이다. 아파트 추정치는 그 빌드의 단지/학교 비율
8.9를 각 학교 수에 적용한 것이다. 공개 지역은 웨이브마다 늘어나므로 이 표는
시점 기록이며, **결정은 "전국 규모에서도 견디는가"로만 내린다.**

측정된 현재 빌드: `npm run build` 14.0초 (vite 6.42초), 번들 559 kB /
gzip 173 kB.

Vercel 제약: 빌드 출력 파일 수에 상한은 없으나 10만 개 이상에서 빌드 시간이
크게 늘어난다. **빌드가 45분을 넘기면 실패한다.**

## 선택지

### A. 빌드 시점 정적 생성 (SSG)

모든 상세 페이지를 빌드 때 HTML로 렌더한다.

- **장점**: 인프라가 가장 단순하다. CDN에서만 서빙된다. 런타임 비용 0
- **단점**:
  - 현재 규모는 45분 안에 들어오지만, 전국 63,000페이지는 여유가 크지 않다.
    빌드는 수만 행의 데이터 조회 페이지네이션도 포함한다
  - **ETL이 갱신될 때마다 전체 재빌드·재배포가 필요하다.** 되풀이 ETL이
    주기적으로 도는 제품에서 이는 구조적 마찰이다
  - 데이터 신선도가 배포 주기에 묶인다. 컨셉 11절 원칙 4(기준일 노출)와
    어울리지 않는다

### B. 상세 경로 한정 서버리스 프리렌더 ← 권고

지도 앱 본체는 SPA로 유지하고, `/school/:id`, `/apt/:id`, `/region/:code`
요청만 Vercel 서버리스 함수가 처리한다. 함수는 Supabase에서 해당 행을 읽어
**콘텐츠가 담긴 HTML**을 만들어 돌려주고, 그 위에 기존 SPA 번들이 하이드레이트
한다.

핵심은 **React SSR을 할 필요가 없다는 것**이다. 크롤러에게 필요한 것은
`<title>`, `<meta description>`, `<h1>`, 핵심 수치, 그리고 다른 상세
페이지로 가는 링크다. 함수는 이 골격만 문자열로 생성하면 되고, 지도·바텀시트·
마커 매니저는 전혀 서버에서 돌 필요가 없다. 컨셉 7절의 화면 모델이 이것을
가능하게 한다 — 외부 진입은 전체 화면 상세이고, 전체 화면 상세는 지도를
포함하지 않는다.

- **장점**:
  - 빌드 시간이 지금과 같다. 페이지 수가 63,000이든 630,000이든 무관하다
  - ETL 갱신이 즉시 반영된다. 재배포 불필요
  - `s-maxage` + `stale-while-revalidate`로 CDN 캐시하면 함수 호출은
    캐시 미스에서만 발생한다
  - 기존 Vite·AppContext·마커 구조를 건드리지 않는다. 검증된 smoke 게이트가
    그대로 유지된다
- **단점**:
  - 프리렌더 HTML과 SPA가 표현하는 내용이 갈라질 수 있다. 두 벌을 만들지
    않도록 데이터→요약 매핑을 공유 모듈 하나로 두어야 한다
  - 서버 측 Supabase 조회가 생긴다. **anon 키로, 공개 2테이블만** 읽는다.
    service_role 키를 이 경로에 두지 않는다 ([`../architecture/SECURITY_MODEL.md`](../architecture/SECURITY_MODEL.md))
  - 첫 요청 지연이 정적 파일보다 길다 (캐시 히트 후에는 동일)

### C. Next.js 마이그레이션

- **장점**: ISR이 이 문제를 정면으로 해결한다. 메타데이터·사이트맵·이미지가
  프레임워크 기본 기능이 된다. 장기적으로 가장 정공법
- **단점**: 명령형 Naver Maps 마커 관리([`../../src/components/map/MarkerManager.tsx`](../../src/components/map/MarkerManager.tsx),
  `ApartmentMarkerManager.tsx`), 바텀시트 제스처 엔진, `AppContext`의
  단일 `useReducer` 구조를 전부 옮겨야 한다. `public-smoke.mjs`가 의존하는
  `data-testid`·`data-snap-index`·`window.__ELEMENTARY_PERFORMANCE__` 계약도
  재검증해야 한다. 유입 실험을 시작하기 위해 치르기에는 큰 비용이고,
  아직 유입이 0인 시점에 치를 비용은 아니다

## 결정

**B를 채택한다.**

A는 되풀이 ETL과 구조적으로 충돌하고, C는 아직 검증되지 않은 가설(SEO 유입이
실제로 발생한다)을 위해 앱 전체를 재작성한다. B는 가장 적은 변경으로 가설을
검증할 수 있고, 검증되면 C로 가는 길을 막지 않는다.

**B로 유입이 실증된 뒤 규모가 C를 정당화하면 그때 마이그레이션한다.**

## 구현 범위

1. `react-router` 도입, `/school/:id`, `/apt/:id`, `/region/:code`, `/compare` 경로
2. [`vercel.json`](../../../vercel.json)의 전면 rewrite를 경로별로 분리 —
   상세 경로는 함수로, 나머지는 `index.html`로
3. 상세 경로 서버리스 함수: anon 키로 공개 2테이블 조회 →
   메타 + 콘텐츠 HTML 생성 → `s-maxage=3600, stale-while-revalidate=86400`
4. 요약 문구·수치 포맷을 클라이언트와 공유하는 단일 모듈
5. `public/` 생성 후 `robots.txt`, `sitemap.xml`. 현재 규모는 단일 사이트맵
   상한(5만 URL) 안에 들어가지만 **학교/아파트/지역으로 분할**한다 — 타입별
   색인률을 따로 봐야 진단이 되고, 전국 확장 시 상한도 넘는다
6. 구글 서치콘솔·네이버 서치어드바이저 등록 및 사이트맵 제출.
   IndexNow는 Bing 계열 대상이며 네이버는 참여사가 아니므로, 네이버는
   서치어드바이저 자체 제출 경로를 쓴다

측정 쪽 상세는 [`../product/MEASUREMENT_PLAN.md`](../product/MEASUREMENT_PLAN.md).

## 선행 조건

URL에 들어가는 아파트 식별자가 영속적이어야 한다.
[`../reference/REPORT_CONCEPT_PREFLIGHT_20260926.md`](../reference/REPORT_CONCEPT_PREFLIGHT_20260926.md) 2.4절의
**공개 슬러그 도입이 이 ADR의 구현보다 먼저 와야 한다.** 식별자가 바뀌면
색인된 URL이 통째로 무효가 되므로, 순서를 뒤집으면 이 ADR의 목적 자체가
사라진다.

## 결과

- 지도 앱과 상세 페이지가 서로 다른 렌더링 경로를 갖게 된다. 상세 콘텐츠의
  단일 출처를 코드로 강제해야 갈라지지 않는다
- 서버 측 Supabase 조회 경로가 처음 생긴다. 공개 데이터 계약
  ([`../architecture/DATA_CONTRACTS.md`](../architecture/DATA_CONTRACTS.md))의
  2테이블 경계가 여기서도 지켜져야 한다
- `public-smoke.mjs`에 상세 경로 직접 진입 케이스를 추가해야 한다
