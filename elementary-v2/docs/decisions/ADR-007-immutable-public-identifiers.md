# ADR-007: 공개 URL은 불변 슬러그를 쓰고, 내부 식별자를 노출하지 않는다

Status: Accepted
Date: 2026-09-29
Context: [ADR-006](ADR-006-detail-page-rendering.md) 선행 조건 1,
[제품 컨셉 12절 0단계 항목 2](../product/PRODUCT_CONCEPT.md)

## 문제

공유 링크와 검색엔진 색인은 **주소가 영구히 바뀌지 않는다**는 전제 위에 선다.
주소가 바뀌면 카카오톡으로 보낸 링크가 죽고, 색인된 페이지가 사라지고, 측정
데이터가 과거와 끊긴다.

학교는 안전하다. `school_id`는 교육부 학교 표준데이터가 부여한
`B##########` 형태이고 파이프라인이 만들지 않는다.

**아파트는 안전하지 않다.** `canonical_complex_id`는 K-apt 매칭 결과에 따라
접두사 자체가 달라진다.

```python
"canonical_complex_id": f"KAPT:{match['kapt_code']}" if match else f"APT:{apt_id}"
```

2026-09-29 운영 데이터 실측:

| | 수 | 비율 |
| --- | --- | --- |
| 고유 단지 | 45,853 | |
| `APT:` (매칭 실패 시 형태) | **27,407** | **59.8%** |
| `KAPT:` | 18,446 | 40.2% |

세 가지 경로로 바뀐다.

1. **접두사 이동** — 지금 매칭에 실패한 단지가 다음 빌드에서 성공하면
   `APT:x` → `KAPT:y`. 수도권 실측에서 고위험군이 6.4%였다.
2. **병합** — 여러 `apt_cd`가 한 K-apt 코드로 묶이면 두 식별자가 하나가 된다.
3. **기준자료 교체** — `APT:` 식별자의 뿌리인 `apt_cd`는
   `archive/GAS/GAS/임시/apt_mst_info_202410.csv`라는 2024-10자 고정 파일에서
   온다. 이 파일을 갱신 가능한 원천으로 바꾸는 날 27,407개가 한꺼번에 바뀐다.

즉 **내부 식별자를 URL에 쓰면 URL이 데이터 파이프라인의 사정에 묶인다.**

## 요구사항

1. 한 번 부여하면 **절대 바뀌지 않는다**
2. 병합·분할이 일어나도 기존 주소가 죽지 않는다
3. 재빌드 간 같은 단지를 다시 찾아 같은 슬러그를 붙일 수 있다
4. URL에서 읽을 수 있어 공유했을 때 신뢰가 간다
5. 45,853개에서 충돌하지 않고, 10만 단위로 늘어도 견딘다
6. **URL을 세상에 공개하기 전에** 부여돼 있어야 한다

## 결정

### 1. 불변 공개 키를 따로 발급한다

`complex_public_key` — **무의미한(opaque) 고정 문자열**이다.

- Crockford Base32, 대문자 8자 (`0-9`, `A-Z` 중 `I`·`L`·`O`·`U` 제외)
- 예: `K7M9Q2XT`
- 대소문자를 구분하지 않는다. 저장은 대문자, 읽기는 아무 대소문자나 허용하고
  정규형으로 리다이렉트한다
- 혼동 문자를 뺀 이유는 사람이 손으로 옮겨 적거나 전화로 읽어줄 수 있어야 하기
  때문이다

**한 번 저장하면 다시 계산하지 않는다.** 이름·주소·`canonical_complex_id` 등
무엇으로부터도 파생시키지 않는다. 파생시키는 순간 그 원본이 바뀔 때 함께
바뀌므로 불변이 아니다.

충돌은 엔트로피가 아니라 **유니크 제약이 보장한다.** 32⁸ ≈ 1.1×10¹²이지만
10만 개 규모에서 생일 문제로 충돌 확률이 0이 아니므로, 제약 위반 시 재생성한다.

### 2. 슬러그는 `canonical_complex_id`가 아니라 **구성 원자**에 고정한다

이게 설계의 핵심이다. 단지는 `apt_cd`들의 묶음이고,
`component_apt_ids` 컬럼에 100% 채워져 있다.

```
단지 = { apt_cd, apt_cd, ... }      ← 이 원자 집합이 재결합의 기준
```

묶는 방식(K-apt 매칭)이 바뀌어도 원자는 남는다.

**이 방식이 성립하는지 실측으로 확인했다.** 재결합이 결정적이려면 한 원자가 두
단지에 속하는 일이 없어야 한다.

| 확인 | 결과 |
| --- | --- |
| 고유 원자 수 | 20,421 |
| **두 단지 이상에 속한 원자** | **0** |
| `canonical_complex_id` 중복 | 0 |
| 구성 원자 1개인 단지 | 19,950 (98.9%) |
| 구성 원자 2개 이상 | 214 |

원자가 단지를 유일하게 결정하므로 재결합에 모호함이 없다. 이것이 이 설계의
유일한 핵심 가정이고, 현재 데이터에서 성립한다. **가정이 깨지면 재결합이 조용히
틀리므로 ETL 감사가 이 불변식을 계속 검사해야 한다.**

**비공개 레지스트리 테이블**이 슬러그와 원자를 잇는다.

슬러그 자체와 슬러그↔원자 관계는 수명이 다르므로 테이블을 나눈다. 원자는
재빌드마다 들고 나지만 슬러그는 한 번 발급되면 영구히 남는다.

```
apartment_public_key            (비공개)  슬러그 그 자체
  public_key      TEXT PRIMARY KEY        발급 후 절대 변경하지 않는다
  issued_at       DATE   NOT NULL
  superseded_by   TEXT   NULL REFERENCES apartment_public_key(public_key)
                                          병합 시 승계 대상. 리다이렉트 근거

apartment_public_key_atom       (비공개)  슬러그가 덮는 구성 원자
  public_key      TEXT   NOT NULL REFERENCES apartment_public_key(public_key)
  apt_cd          TEXT   NOT NULL
  first_seen_at   DATE   NOT NULL
  PRIMARY KEY (public_key, apt_cd)
  UNIQUE (apt_cd)                         ← 한 원자는 한 슬러그에만 속한다
```

`UNIQUE (apt_cd)`가 이 설계의 불변식을 **데이터베이스가 강제하게** 만든다.
실측에서 원자 20,421개 중 두 단지에 걸친 것이 0개였고, 그 성질이 깨지면 적재가
실패해 조용히 틀리는 대신 시끄럽게 멈춘다.

`superseded_by`가 채워진 슬러그는 더 이상 정규형이 아니지만 **행을 삭제하지
않는다.** 그것이 과거 링크를 살리는 유일한 근거다.

### 3. 재빌드 때의 재결합 규칙

새로 만들어진 단지마다 그 단지의 원자들로 레지스트리를 조회한다.

| 조회 결과 | 상황 | 처리 |
| --- | --- | --- |
| 슬러그 1개 | 평범한 재빌드. 접두사가 바뀌었어도 원자는 같다 | **그 슬러그를 그대로 쓴다** |
| 슬러그 2개 이상 | 병합 | 아래 순서로 정규형을 고르고, 나머지는 `superseded_by`를 채워 **리다이렉트** |
| 0개 | 신규 단지 | 새 슬러그 발급 |
| 기존 슬러그의 원자가 둘로 갈림 | 분할 | 아래 순서로 한쪽이 슬러그를 유지하고, 다른 쪽은 신규 발급 |

#### 정규형 선택 순서 — 변하지 않는 값만 쓴다

1. **덮는 원자 수가 많은 슬러그**
2. 같으면 **`issued_at`이 이른 슬러그**
3. 같으면 **`public_key`가 사전순으로 앞선 슬러그**

세 기준 모두 발급 후 변하지 않는 값이다. **이것이 요건이다.** 세대수처럼
보정되는 값으로 고르면 재빌드마다 정규형이 뒤바뀌고, 정규 URL이 바뀌는 것은
링크가 죽는 것과 같은 문제다.

1번만으로는 부족하다는 것을 실측으로 확인했다. 병합 대기 중인 187개 단지는
**전부 단일 원자**여서, 85건 전부가 1번에서 동점이 된다. 2·3번이 없으면
정규형을 고르지 못한다.

**경로 1이 오늘의 6.4% 문제를 해결한다.** `APT:` → `KAPT:` 이동은 원자가
그대로이므로 슬러그가 유지된다.

**경로 2(병합)는 가설이 아니라 이미 대기 중이다.** 187개 단지가 85개의
`kapt_code`를 공유하면서 `group_type = shared_review_unmerged` 상태로 남아 있다.
빌더가 식별자 충돌을 피하려고 일부러 병합하지 않고 `APT:` 형태를 유지한 것이다
(I-03 검토 대기 항목). 그 검토가 종결되면 **187개가 85개로 합쳐지고, 슬러그
102개가 리다이렉트로 전환된다.** 이 ADR 없이 그 일이 일어나면 102개 주소가
그냥 죽는다.

**다만 조건이 있다. 슬러그가 병합보다 먼저 발급돼 있어야 한다.** 먼저 발급돼
있으면 187개가 각자 슬러그를 갖고, 병합 시 원자 조회가 슬러그 2개를 찾아
리다이렉트를 만든다. 병합이 먼저 일어나면 슬러그는 85개만 생기고 102개는
애초에 존재하지 않는다 — 그 경우에도 링크가 죽지는 않지만, **공개 전에
발급한다**는 이 ADR의 전제가 지켜져야 성립한다.

**경로 3(기준자료 교체)은 이 규칙으로 해결되지 않는다.** `apt_cd` 자체가
바뀌므로 주소·단지명으로 다시 이어야 하고, 그것은 별도 마이그레이션이다.
레지스트리는 그 작업을 **기록하고 리다이렉트를 낼 자리**를 제공한다. 지금
아무것도 없는 상태보다는 낫지만, 무료로 해결되지는 않는다.

### 4. URL 모양 — 사람이 읽는 부분과 진실을 분리한다

```
/school/서울-강남구-서울대현초등학교--B000002292
/apt/서울-강남구-은마--K7M9Q2XT
```

- **마지막 `--` 뒤의 값만 권위를 가진다.** 앞부분은 장식이며 읽을 때 무시한다
- 앞부분이 현재 이름과 다르면 정규형으로 **301 리다이렉트**한다
- 따라서 **단지명이 바뀌어도 링크가 죽지 않는다.** 이름은 표시용일 뿐이다

아파트는 이름이 바뀐다(`apartment_name_history` 테이블이 존재하는 이유다).
이름을 URL의 진실로 삼으면 개명될 때마다 링크가 죽는다. 이 구조는 **읽을 수
있으면서 불변**이라는 두 요구를 동시에 만족시키는 유일한 방법이다.

#### 지역명을 반드시 넣어야 하는 이유

`은마`를 조회해 보면 **전국에 4개 단지**가 있다.

| 단지 | 지역 | 배정 학교 |
| --- | --- | --- |
| 은마 | 서울 강남구 | 서울대현초등학교 (대표), 서울대곡초등학교 |
| 은마 | 대구 북구 | 대구태현초등학교 |
| 은마 | 전북 전주시 | 전주서신초등학교 |
| 은마 | 경남 창원시 | 구암초등학교 |

이름만으로는 검색 결과에서 네 페이지가 구분되지 않는다. **지역이 URL과 제목에
모두 들어가야 서로 잡아먹지 않는다.**

#### 검색 결과에 실제로 어떻게 보이나

##### 아파트 상세 — 서울 강남구 은마

```
어디초
https://…/apt/서울-강남구-은마--K7M9Q2XT
은마 배정 초등학교 · 서울 강남구 | 어디초
서울 강남구 은마(4,424세대 · 28개 동 · 1979년)의 공식 배정 초등학교는
서울대현초등학교입니다. 서울대곡초등학교에도 배정될 수 있습니다.
1학년 99명 · 4학급. 2026-03-20 기준.
```

- **제목** `{단지명} 배정 초등학교 · {시도} {시군구} | 어디초`
- **설명** 규모(세대수·동수·연식) → **대표 배정 학교** → 복수 배정이면 그 사실
  → 1학년 규모 → **기준일**

복수 배정을 설명에 넣는 것은 [컨셉 11절 원칙 2](../product/PRODUCT_CONCEPT.md)
때문이다. 은마는 실제로 두 학교에 배정되며, 검색 결과에서 한 곳만 보여주면
그 자체가 오해를 만든다.

##### 학교 상세 — 서울대현초등학교

```
어디초
https://…/school/서울-강남구-서울대현초등학교--B000002292
서울대현초등학교 배정 아파트 23곳 · 서울 강남구 | 어디초
서울 강남구 서울대현초등학교에 배정되는 아파트 23개 단지, 총 8,324세대.
1학년 99명 · 4학급 · 학급당 24.8명. 2026-03-20 기준 공식 통학구역 자료.
```

- **제목** `{학교명} 배정 아파트 {N}곳 · {시도} {시군구} | 어디초`
- **설명** 배정 단지 수·총세대수 → 1학년 규모 → **기준일과 근거**

제목에 `배정 아파트 {N}곳`을 넣는 이유는, 이 제품이 답하는 질문이 "이 학교에
어떤 아파트가 배정되나"이고 그 숫자가 페이지마다 달라 **검색 결과에서 서로
구별되기 때문**이다.

#### 중복 콘텐츠 — 이 URL 구조가 만드는 위험

앞부분이 장식이라는 것은 **같은 페이지에 무한히 많은 주소가 생긴다**는 뜻이다.
`/apt/아무거나--K7M9Q2XT`도 같은 페이지를 연다. 검색엔진에는 중복 콘텐츠로
보이고, 방치하면 색인에서 불이익을 받는다.

세 가지를 반드시 함께 구현한다.

1. 모든 페이지에 **`<link rel="canonical">`** 을 정규 주소로 넣는다
2. 앞부분이 정규형과 다르면 **301 리다이렉트**한다
3. **사이트맵에는 정규형만** 싣는다

셋 중 하나라도 빠지면 이 URL 구조의 이점보다 손해가 커진다.

### 5. 학교는 슬러그를 발급하지 않는다

`school_id`를 키 자리에 그대로 넣고 URL 모양만 같이 쓴다. 2026-09-29 실측:

| 확인 | 결과 |
| --- | --- |
| 학교 수 | 6,302 |
| `school_id` 고유 | 6,302 (중복 0) |
| 형태 | `B#########` 전부 동일 |
| `operation_status` | 전부 `운영` |

**따라서 슬러그 발급 작업은 아파트에만 필요하다.** 학교는 URL 모양을 맞추는 것
외에 추가 작업이 없다.

학교에도 아파트와 같은 위험이 있는지 따져봤고, 성질이 다르다.

- **번호가 재사용되지 않는다.** 폐교해도 그 `school_id`가 다른 학교에 붙지
  않으므로, 링크가 **엉뚱한 학교를 가리키는 일은 없다.**
- **폐교는 404가 아니라 상태로 처리한다.** `operation_status`가 이미 공개
  계약에 있으므로, 운영이 끝난 학교는 그 사실을 밝히는 페이지를 낸다.
  [컨셉 11절 원칙 2](../product/PRODUCT_CONCEPT.md)에 따라 조용히 다른 학교로
  넘기지 않는다.
- **상위 원천에 없는 학교는 URL이 애초에 없다.** 참미르초·신연초처럼 학교
  표준데이터에 빠진 학교는 `school_master`에 없다. 나중에 공시되면 주소가
  새로 생기는 것이지, 기존 주소가 바뀌는 것이 아니다.

**한글을 넣는다** (2026-09-29 결정). 검색 결과와 주소창에 보이는 것은 디코딩된
한글이고, 한국 검색엔진에서 URL에 키워드가 있는 이점이 있다. 일부 환경에서
복사하면 `%EC%9D%80%EB%A7%88` 형태로 보이는 것은 감수한다.

사람이 읽는 부분은 **`{시도약칭}-{시군구}-{이름}`으로 고정**한다. 이름에 지역명이
이미 들어 있어 `서울-강남구-서울대현초등학교`처럼 겹쳐도 그대로 둔다. 규칙이
단순해야 매 요청마다 같은 결과가 나오고, 그래야 불필요한 리다이렉트가 생기지
않는다. URL의 중복은 무해하지만 규칙의 복잡함은 버그를 만든다.

## 지금 해야 하는 이유

**URL을 공개한 뒤에 슬러그를 도입하면 그때까지 색인된 주소를 전부 버려야
한다.** 이 작업은 라우팅([ADR-006](ADR-006-detail-page-rendering.md))보다
먼저 와야 하고, ADR-006은 라우팅보다 먼저 배포 경로가 살아 있어야 한다는 조건을
갖는다. 그 조건은 2026-09-28에 해소됐다.

```
슬러그 발급  →  라우팅·URL  →  프리렌더·사이트맵  →  검색엔진 제출
```

순서를 바꿀 수 없는 사슬이다.

## 검토했으나 채택하지 않은 것

**내부 식별자를 그대로 쓴다** — 문제 그 자체다. 27,407개가 파이프라인 사정에
따라 바뀐다.

**단지명 슬러그** (`/apt/은마-강남구`) — 개명 시 링크가 죽는다. 동명 단지도
있다(`은마`는 서울과 대구에 모두 존재하며, 이 때문에 smoke의 중복제거 검증이
한 번 깨졌다).

**순번 공개 ID** (`/apt/12345`) — 불변이고 짧지만 전체 개수가 드러나고 순회
수집이 쉽다. 읽을 수 있는 정보가 전혀 없어 공유 시 신뢰도 낮다.

**로마자 변환 슬러그** (`/apt/eunma-gangnam`) — 변환 규칙이 확정적이지 않고,
한국 사용자가 그렇게 검색하지 않는다.

**주소 기반 슬러그** — 행정구역이 개편된다. 이 프로젝트에서 이미 겪었다:
광주·전남 통합(2026-07-01), 강원·전북의 특별자치도 전환으로 법정동 코드까지
바뀌었다.

> ```
>

실제 데이터로 확인한 것:

| 시나리오 | 결과 |
| --- | --- |
| 최초 발급 (20,164 단지) | 20,164개 발급 |
| 동일 입력 재빌드 | **20,164개 전부 재사용, 신규 0** |

세 번째가 이 설계의 목적 그 자체다. ADR 없이 그 병합이 일어나면 102개 주소가
죽고, 있으면 전부 리다이렉트로 살아남는다.

**적용은 `SUPABASE_SERVICE_KEY`가 필요해 이 작업에서 수행하지 않았다.**
마이그레이션 적용과 운영 발급은 권한 있는 사람이 실행한다.

## 결과

- 공개 URL이 ETL 내부 사정과 분리된다. 파이프라인은 자유롭게 재빌드할 수 있다
- 비공개 테이블 하나와 공개 컬럼 하나가 늘어난다
- 재빌드마다 재결합 단계가 추가된다. 결합에 실패한 단지는 새 슬러그를 받으므로,
  **재결합 실패율을 ETL 감사 항목으로 넣어야 한다.** 조용히 실패하면 링크가
  조용히 죽는다
- 병합·분할은 리다이렉트로 처리되며, 그 기록이 레지스트리에 남는다
- 기준자료 교체는 여전히 계획된 마이그레이션을 요구한다. 이 ADR은 그것을
  없애지 않고, 그때 링크를 살릴 수단을 마련한다
